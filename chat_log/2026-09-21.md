## 이 저장소에 대한 이해

### 무엇을 위한 저장소인가

이것은 **LLM이 직접 유지보수하는 개인 지식베이스**입니다. 단순히 메모를 모아두는 곳이 아니라, LLM agent가 원본 자료를 읽고 지식을 추출·정리·연결하여 시간이 지날수록 점점 성장하는 구조입니다.

---

### 디렉토리 구조와 역할

| 디렉토리 | 역할 |
|----------|------|
| `raw/` | 원본 자료 보관소. 에러 로그, 논문, 강의 노트 등. **수정 금지** (source of truth) |
| `wiki/` | LLM이 정리한 지식 문서들. OKF 포맷을 따름 |
| `references/` | 운영 철학과 포맷 스펙 문서. **수정 금지** |
| `assets/` | 이미지, 첨부파일 |
| `index.md` | 전체 지식베이스의 진입점 |
| `log.md` | 시간순 변경 이력 |
| `AGENTS.md` | LLM agent가 따라야 할 운영 규칙 |

---

### 문서 포맷 (OKF)

`wiki/` 안의 모든 문서는 반드시 YAML frontmatter로 시작해야 합니다:

```yaml
---
type: Concept   # 또는 Error Note / Project / Paper Note 등
title:
description:
tags: []
timestamp:
status: active
---
```

문서 타입마다 권장 섹션 구조가 다릅니다. 예를 들어 Paper Note는 "How I Can Use This" 섹션이 필수이고, Error Note는 원인과 해결 방법을 명확히 분리합니다.

---

### LLM agent의 주요 작업 흐름

**Ingest (새 자료 입력 시)**
`raw/` 읽기 → 핵심 추출 → `wiki/` 문서 생성 또는 갱신 → 관련 문서 cross-link 추가 → `index.md`와 `log.md` 갱신

**Query (질문 답변 시)**
`index.md` 확인 → 관련 wiki 문서 탐색 → 필요하면 raw 확인 → 답변. wiki에 없으면 "모른다"고 말하고 조사 방향 제안

**Lint (상태 점검 시)**
frontmatter 누락, 깨진 링크, 고아 문서, 중복, index/log 미반영 항목 등을 점검

---

### 핵심 원칙 요약

- 문서는 작고 명확한 단위로 유지 (하나의 파일 = 하나의 개념)
- 관련 문서 간 cross-link는 적극적으로 추가 (에러 ↔ 프로젝트, 논문 ↔ 적용 프로젝트 등)
- 새 문서 생성 시 반드시 `index.md`와 `log.md` 갱신
- 한국어 기본, 기술 용어는 영어 병기
- 추측은 추측이라 표시, 사실과 해석 구분
- git commit은 `docs:`, `chore:`, `lint:` 접두어 사용

---

한 마디로: **"LLM이 사서 역할을 하는 개인 도서관"** 이라고 이해했습니다. 원본 자료(`raw/`)는 건드리지 않고, LLM이 그것을 읽어 정제된 지식 문서(`wiki/`)를 만들고 유지하는 구조입니다.

## 1. 이 저장소가 존재하는 이유

일반적인 메모 앱(Notion, Obsidian 등)은 **사람이 직접 정리**해야 합니다. 이 저장소는 다릅니다. **LLM이 정리 담당자**입니다.

핵심 철학은 이렇습니다:

> "원본 자료를 던져주면, LLM이 알아서 읽고, 기존 지식과 연결하고, 문서를 만들고, 업데이트한다."

시간이 지날수록 지식이 **누적되고 연결**되어야 하기 때문에, LLM이 따라야 할 규칙을 명문화한 것이 `AGENTS.md`입니다.

---

## 2. `raw/` vs `wiki/` — 가장 중요한 구분

| | `raw/` | `wiki/` |
|---|---|---|
| 내용 | 원본 그대로 | LLM이 정제한 것 |
| 수정 | 금지 (사용자 요청 시만) | LLM이 자유롭게 |
| 형식 | 제약 없음 | OKF 포맷 필수 |
| 예시 | 에러 로그, 논문 PDF 텍스트, 강의 노트 원본 | 개념 문서, 에러 정리, 프로젝트 문서 |

`raw/`는 **source of truth**입니다. 나중에 wiki 문서 내용이 틀렸어도 raw를 보면 원래 사실을 확인할 수 있습니다.

---

## 3. OKF 포맷 — 문서가 따라야 할 구조

`wiki/` 안의 모든 문서는 반드시 **YAML frontmatter**로 시작합니다.

```yaml
---
type: Concept
title: 경사 하강법
description: 손실 함수를 최소화하기 위해 기울기 반대 방향으로 이동하는 최적화 알고리즘
tags: [ml, optimization]
timestamp: 2026-09-20
status: active
---
```

이렇게 하는 이유는 **LLM이 나중에 검색하고 연결하기 쉽게** 하기 위해서입니다. 구조가 통일되어 있어야 "이 문서가 어떤 종류인지", "현재 상태가 뭔지" 빠르게 파악할 수 있습니다.

### 문서 타입별 섹션 구조

타입마다 권장 섹션이 다릅니다. 중요한 타입 세 가지를 보면:

**Concept** (개념 문서)
```
# Summary
# Why it matters
# Key Ideas
# Examples
# Related Concepts
# Citations
```

**Error Note** (에러 정리)
```
# Situation      ← 어떤 상황에서 발생했는지
# Error Message  ← 실제 에러 메시지
# Cause          ← 원인
# Solution       ← 해결 방법
# Prevention     ← 예방법
# Related Concepts
```

**Paper Note** (논문 정리)
```
# One-line Summary
# Problem
# Method
# Experiments
# Key Findings
# My Understanding
# How I Can Use This   ← 이 섹션이 핵심: "내가 어디에 써먹을 수 있나"
# Open Questions
```

특히 논문 노트에서 **"How I Can Use This"** 를 필수로 요구하는 점이 인상적입니다. 논문을 단순히 이해하는 데서 그치지 않고, 실용적 연결을 강제하는 구조입니다.

## 4. 세 가지 핵심 워크플로우

### Ingest — 새 자료가 들어왔을 때

```
raw/ 원본 읽기
  ↓
핵심 내용 추출
  ↓
새 wiki 문서 필요? → 생성
기존 wiki 문서에 추가할 내용? → 업데이트
  ↓
관련 문서에 cross-link 추가
  ↓
index.md 갱신 + log.md에 기록
```

원본 자료 하나가 **여러 wiki 문서를 동시에 업데이트**할 수 있습니다. 예를 들어 새 에러 로그가 들어오면, 에러 문서를 만들고 + 관련 프로젝트 문서에 링크를 추가하고 + 관련 설치 가이드도 업데이트할 수 있습니다.

### Query — 사용자가 질문했을 때

LLM이 즉흥적으로 답하지 않고, 반드시 이 순서를 따릅니다:

1. `index.md` 먼저 확인 (어디를 봐야 할지 파악)
2. 관련 wiki 문서 탐색
3. 필요하면 raw 확인
4. 답변 작성
5. **"wiki에 정리할 가치가 있다면 저장할 것을 제안"**

마지막 단계가 중요합니다. 질문에 답하면서도 지식베이스를 성장시킬 기회를 놓치지 않습니다. wiki에 없는 내용이면 **"모른다"고 말하고 조사 방향을 제안**합니다 — 추측해서 채우지 않습니다.

### Lint — 상태 점검

정기적으로 wiki 전체를 점검합니다. 체크 항목:

- frontmatter 누락 문서
- 깨진 링크 (링크 대상이 사라진 것)
- **고립된 문서** (어디에서도 링크되지 않는 문서)
- 중복 문서
- `index.md`에 등록 안 된 문서
- `log.md`에 기록 안 된 큰 변경

결과는 `wiki/_maintenance/` 아래에 기록합니다.

## 5. Cross-link — 지식을 연결하는 규칙

단순히 문서를 만드는 것이 아니라, **문서 간 연결**이 이 시스템의 핵심 가치입니다. 특히 아래 관계는 반드시 연결하도록 규정되어 있습니다:

| 연결 관계 | 이유 |
|-----------|------|
| 에러 ↔ 프로젝트 | 어떤 프로젝트에서 그 에러가 났는지 추적 |
| 에러 ↔ 설치 가이드 | 환경 설정 문제인 경우 참조 |
| 개념 ↔ 예제 코드 | 이론과 실습을 연결 |
| 논문 ↔ 적용 가능한 프로젝트 | 논문을 실제로 써먹을 곳과 연결 |
| CS 개념 ↔ 알고리즘 문제 | 개념과 문제풀이 연결 |

링크 형식은 repository-relative 경로를 사용합니다:
```markdown
See [경사 하강법](../ml/gradient-descent.md).
```

## 1. `llm-wiki.md` — LLM Wiki 방법론 가이드

이 문서는 이 저장소 전체의 **철학적 근간**입니다. "왜 이렇게 만들었는가"를 설명합니다.

**핵심 주장: RAG와 LLM Wiki의 차이**

대부분의 사람들이 LLM + 문서를 쓰는 방식은 **RAG**입니다. 질문할 때마다 문서를 검색해서 그때그때 답을 만들어냅니다. 지식이 누적되지 않고, 매번 처음부터 다시 조합합니다.

이 방법론은 다릅니다. LLM이 원본 자료를 읽고 **한 번 정리해서 wiki에 저장**합니다. 다음에 또 질문하면 이미 정리된 wiki를 읽으면 됩니다. 시간이 지날수록 wiki가 풍부해지는 **누적 구조**입니다.

비유하자면:
- RAG = 매번 도서관에서 책을 찾아 읽는 것
- LLM Wiki = 책을 읽고 요약·정리해서 내 노트에 쌓아두는 것

**3개 레이어 구조**

| 레이어 | 역할 |
|--------|------|
| Raw sources | 원본 자료. 수정 불가. source of truth |
| Wiki | LLM이 작성·유지하는 정제된 지식 문서 |
| Schema | AGENTS.md처럼 LLM이 따라야 할 운영 규칙 |

**흥미로운 표현**: "Obsidian은 IDE, LLM은 프로그래머, wiki는 코드베이스" — 즉 사람은 결과물을 보고 방향을 잡고, LLM이 실제 작업을 합니다.

**왜 작동하는가에 대한 설명도 포함됩니다.** 사람이 wiki를 포기하는 이유는 유지보수가 귀찮기 때문인데, LLM은 지치지 않고 cross-link 추가, 요약 갱신, 모순 표시 등을 계속 해줍니다.

마지막에 "이 문서는 의도적으로 추상적으로 작성되었다"고 명시합니다 — 구체적인 구현은 사용자와 LLM이 함께 만들어가라는 의미입니다.

## 2. `okf-spec.md` — Open Knowledge Format 명세서

이 문서는 `wiki/` 안의 모든 문서가 따라야 하는 **포맷의 공식 명세**입니다. 버전 0.1 draft입니다.

**왜 이 포맷이 필요한가**

AI agent가 늘어나면서 지식 표현 방식이 제각각 생겨나고 있습니다. OKF는 이를 통일하기 위한 시도로, 4가지 원칙을 따릅니다:

- 도구 없이 **사람이 읽을 수 있어야** 한다
- SDK 없이 **agent가 파싱할 수 있어야** 한다
- git에서 **diff가 가능해야** 한다
- 도구와 조직을 넘어 **이동 가능해야** 한다

**핵심 구조**

모든 문서는 두 부분으로 구성됩니다:

1. **YAML frontmatter** — `type` 필드만 필수. 나머지(title, description, tags, timestamp)는 권장
2. **Markdown body** — 자유 형식. 단, 구조적 마크다운(헤딩, 리스트, 테이블)을 권장

**중요한 규칙들**

- `index.md`와 `log.md`는 **예약된 파일명** — 일반 개념 문서로 쓰면 안 됨
- 링크는 bundle-relative(`/tables/users.md`) 또는 relative(`./other.md`) 둘 다 허용
- **깨진 링크는 에러가 아님** — 아직 작성되지 않은 지식일 수 있으므로 무시
- `type` 값은 중앙 등록 없이 자유롭게 지정 가능 (단, 설명적이어야 함)

**준수(Conformance) 기준**은 딱 3가지만:
1. 모든 `.md` 파일에 YAML frontmatter 있어야 함
2. frontmatter에 `type` 필드 있어야 함
3. `index.md`, `log.md`는 지정된 형식을 따라야 함

나머지는 모두 soft guidance입니다.

이것이 이 문서 전체의 핵심입니다. 22개 세부 항목은 모두 이 목적을 구현하기 위한 구체적인 방법론입니다.

### 핵심 원칙들을 영역별로 이해한 내용

**[대화 태도 — 섹션 2]**

칭찬 표현("좋은 질문입니다", "훌륭한 접근입니다")을 습관적으로 사용하지 않는다. 단, 질문이 실험 설계, 모델 선택, 원인 분석 등 실무적으로 실제 의미가 있는 경우에는 칭찬해도 되는데, 그 경우에도 **왜 중요한 질문인지 구체적으로 설명해야 한다.** 예시가 매우 인상적입니다:

> "이 질문은 중요합니다. 현재 실험의 성능 향상이 데이터 증강 때문인지 단순한 분포 변화 때문인지 구분하지 않으면 이후 실험 결과를 잘못 해석할 수 있기 때문입니다."

아첨을 금지하는 것이 목적이 아니라, **근거 없는 평가를 금지**하는 것이 목적입니다.

---

**[설명 순서 — 섹션 3]**

모든 기술 설명은 다음 순서를 따릅니다:

1. **기초 개념** — 이 질문을 이해하기 위한 최소한의 선수 지식
2. **원리** — 내부적으로 어떻게 작동하는가
3. **이유** — 왜 그런 설계인가, 왜 그런 결과가 나오는가
4. **직접 답** — 실제 질문에 대한 명확한 답
5. **실제 활용** — 프로젝트에서, 실험에서, 다음 판단에서 무엇을 할 수 있는가

단순히 "정답 → 설명" 구조가 아니라, **질문에 답하기 위한 사고의 경로 전체**를 보여주는 구조입니다.

---

**[비전공자 기준 설명 — 섹션 4]**

중요한 단서가 있습니다: **"비전공자 기준이라는 이유로 핵심 원리를 지나치게 단순화하거나 기술적으로 틀린 설명을 만들지 않는다."** 쉽게 설명하되 정확성을 희생하지 말라는 것입니다.

---

**[영어 용어 처리 — 섹션 5, 6]**

단순 번역이 아니라 **그 용어가 실제로 무엇을 의미하는지** 설명합니다. 예:
- `covariate shift` → 공변량 변화, **입력 데이터의 분포가 달라지는 현상**
- `threshold` → 임계값, **정상/이상을 나누기 위한 기준값**

그리고 기술적 답변 하단에는 두 가지를 구분해 제공합니다:
- **공식적 정의**: 정확성을 위한 학술적 설명
- **비전공자용 풀이**: 이해 가능성을 위한 직관적 설명

---

**[에러 처리 순서 — 섹션 7]**

이 부분이 특히 구체적입니다. 에러가 들어오면 **수정 코드부터 주지 않습니다.**

순서: 에러 메시지 해석 → 원인 → 해결 방법 → 재발 방지

에러 메시지 해석 단계에서 특히 중요한 것은 **"다음에 스스로 읽을 수 있도록 어디서부터 읽어야 하는지 알려준다"** 는 부분입니다. Python traceback이라면 마지막 줄(예외 종류와 메시지)을 먼저 보고, 이후 위쪽 호출 경로를 역으로 추적하는 방법까지 설명합니다.

**[자료 기반 답변과 출처 — 섹션 10, 11, 12, 13]**

사용자가 논문이나 보고서를 제공했을 때 세 가지를 명확히 구분합니다:

**2. `python-teacher.md`와의 관계**

**3. 권장 답변 템플릿(섹션 22) — 결론을 앞에 두는 구조**

섹션 22의 템플릿은 **"1. 결론"** 을 가장 먼저 두고, 그 이후 개념 설명을 전개합니다. 반면 섹션 3의 기본 순서는 **"기초 개념 → 원리 → 이유 → 직접 답"** 순서입니다. 두 구조가 달라 보입니다. 저는 이렇게 해석했습니다: 복잡한 기술 질문에서는 먼저 결론(무엇인지 한 줄)을 제시해서 방향을 잡아주고, 이후 기초 개념부터 순서대로 풀어가는 방식이 가장 자연스러울 것 같습니다. 즉 **결론으로 닻을 내리고, 이해의 경로를 처음부터 따라가게 하는 구조**입니다. 이것도 맞게 이해한 건지 여쭤보고 싶습니다.

## 3. 평가 산식 — 가장 중요한 부분

```
Score = 0.9 × ADS + 0.1 × CPS
```

### ADS (AI-Generated Audio Detection Score) — 전체의 90%

```
ADS = 0.5 × (1 - File EER) + 0.2 × (1 - Voice EER) + 0.3 × (1 - Music EER)
```

EER(Equal Error Rate)는 **낮을수록 좋은 지표**입니다. FPR(False Positive Rate)과 FNR(False Negative Rate)이 같아지는 지점의 오류율로, 0에 가까울수록 탐지 성능이 좋습니다. `(1 - EER)`로 변환해서 사용하므로 **높을수록 좋습니다.**

ADS 내 가중치를 풀어보면:
- **File EER: 0.5** — 가장 중요 (파일 전체의 가짜 판별)
- **Music EER: 0.3** — 두 번째로 중요
- **Voice EER: 0.2** — 세 번째

**중요한 세부 규정**: Voice EER은 음성이 존재하는 샘플에서만, Music EER은 음악이 존재하는 샘플에서만 계산됩니다. 즉 음성이 없는 파일에서 VOICE_FAKE_PROB를 잘못 예측해도 Voice EER에는 반영되지 않습니다.

### CPS (Component Presence Score) — 전체의 10%

```
CPS = 0.5 × Voice Presence ROC-AUC + 0.5 × Music Presence ROC-AUC
```

음성·음악이 존재하는지 판별하는 점수입니다. ROC-AUC를 사용하므로 **높을수록 좋습니다.**

### 배점 구조가 전략적으로 의미하는 것

전체 점수의 90%가 ADS에 걸려 있고, ADS 내에서 Music EER(0.3)이 Voice EER(0.2)보다 가중치가 높습니다. 그런데 베이스라인은 **음성 탐지용으로 설계된 DF-Arena 1B를 음악 탐지에도 그대로 사용**하고 있어서, Music 경로가 가장 취약한 지점입니다. 이것이 이 프로젝트가 Music 경로를 교체하기로 한 전략적 근거입니다.

## `music_fake_pipeline` README에서 확인한 내용

### 이 프로젝트가 무엇인가

`MUSIC_FAKE_PROB` 경로를 교체하기 위한 **완성된 학습 파이프라인**입니다. 코드가 이미 구현되어 있고, 합성(synthetic) 데이터로 end-to-end 검증까지 완료된 상태입니다. 실제 음악 데이터를 채워 넣고 학습을 돌리는 단계가 남아 있습니다.

### 구성 파일과 역할

| 파일 | 역할 |
|------|------|
| `config.py` | 전역 설정 (경로, 오디오 상수, 학습 하이퍼파라미터) |
| `audio_utils.py` | baseline과 동일한 세그먼트 분할/로딩 로직 |
| `demucs_separate.py` | HTDemucs 분리 (baseline 재사용) |
| `features.py` | waveform → log-mel spectrogram 변환 |
| `model.py` | `MusicFakeClassifier` (소형 CNN, **약 25만 파라미터**) |
| `dataset.py` | manifest → PyTorch Dataset |

---

### 기초 개념 — CUDA 연결에 필요한 3개 층

```
[GPU 하드웨어]
      ↑
[NVIDIA 드라이버]   ← GPU와 OS를 연결 (이미 설치돼 있었음)
      ↑
[CUDA Runtime]      ← PyTorch가 GPU에 연산을 보내는 통로
      ↑
[PyTorch 빌드]      ← +cu128 이어야 CUDA Runtime 포함
```

---

### 원리 — 왜 pip install torch 만으로는 안 되는가

PyTorch CUDA 빌드는 파일 크기가 **2~3GB**입니다. PyPI(pip 기본 저장소)는 패키지 크기를 100MB로 제한하기 때문에 CUDA 버전을 올릴 수가 없습니다. 그래서 PyTorch 팀은 별도 휠 서버(`download.pytorch.org/whl/`)를 운영하고, PyPI에는 CPU 전용 버전만 올려둡니다.

`pip install torch`를 아무 옵션 없이 치면 PyPI에서 CPU 버전이 자동으로 내려옵니다.

---

### 직접 답

오늘 겪으신 상황 그대로입니다:

| 명령 | 결과 |
|------|------|
| `pip install torch` | `2.11.0+cpu` (PyPI 기본) |
| `pip install torch==2.11.0+cu128 --index-url https://...` | `2.11.0+cu128` (CUDA 포함) |

드라이버는 이미 설치돼 있었고, `nvidia-smi`도 정상이었지만 PyTorch 빌드가 CPU 전용이라 GPU를 아예 몰랐던 겁니다.

---

### 실제 활용

앞으로 새 환경에서 세팅할 때 체크리스트:

1. `nvidia-smi` → 드라이버·CUDA 버전 확인
2. `pip install torch --index-url https://download.pytorch.org/whl/cu128` → CUDA 빌드 명시
3. `python cuda_check.py` → 연결 확인

```toml
explicit = true

[tool.uv.sources]
torch = { index = "pytorch-cu128" }

```

```
1. nvidia-smi 확인

2. uv venv              ← 가상환경 생성
        ↓
3. pyproject.toml에 인덱스 등록 (위 설정, 최초 1회)
        ↓
4. uv sync              ← 이후 항상 이 한 줄로 끝
```

pip과 비교하면:

| | pip | uv |
|--|--|--|
| CUDA 설치 | 매번 `--index-url` 붙여야 함 | `pyproject.toml`에 한 번 등록하면 `uv sync`로 끝 |
| 가상환경 | `python -m venv` | `uv venv` |
| 속도 | 보통 | 훨씬 빠름 (Rust 기반) |

이 프로젝트도 `pyproject.toml` 만들고 uv로 관리하면 환경 재현이 편해집니다. 원하시면 설정해드릴 수 있습니다.
